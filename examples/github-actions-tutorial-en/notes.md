- Overview of tutorial topics: definition of GitHub Actions, developer workflow use cases, basic concepts (events, actions, workflow), CI/CD pipeline benefits, hands‑on demo with a Java Gradle project built into a Docker image and pushed to a private Docker Hub repository.  
- GitHub Actions is a platform to automate developer workflows, not just a CI/CD tool.  
- Typical developer tasks that can be automated: handling issues, labeling, assigning, reviewing pull requests, releasing new versions, generating release notes, building and testing code.  
- Example project: a Java library for handling date‑time; contributors create issues, fix bugs via pull requests, merge to `master`, then trigger a build/release pipeline.  
- As projects grow, manual management becomes time‑consuming; automation lets developers focus on coding.  
- GitHub Actions reacts to **events** (e.g., issue creation, pull‑request creation, merge, contributor addition) generated by GitHub or integrated tools.  
- For each event, you can configure **actions** (e.g., add a label, assign an issue, run a script to reproduce the issue).  
- A series of actions linked to an event forms a **workflow**.

- GitHub Actions can be used for CI/CD pipelines in both public and private GitHub repositories.  
- Typical CI/CD flow: commit → build → test → create artifact → store artifact → deploy to a server.  
- Advantages of using GitHub Actions over separate CI/CD tools:  
  - No need for a third‑party tool when code is already on GitHub.  
  - Integrated directly with the repository, reducing management overhead.  
  - Easy setup aimed at developers; no dedicated DevOps person required.  
- Compared to tools like Jenkins, GitHub Actions simplifies integration with many technologies (Node.js, Docker, Nexus, AWS, Java/Maven, etc.) without manually installing languages, build tools, or plugins.  
- Users can request specific environments (e.g., Node + Docker) with desired versions directly in the workflow.  
- Demo example: Java Gradle project built into a Docker image and pushed to a private Docker repository.  
- Creating a new repository (e.g., “my‑project”, public) automatically provides an **Actions** tab with workflow templates.  
- Workflow templates are grouped into three categories:  
  1. **Deployment workflows** – deploy code to cloud services or automation tools.  
  2. **Continuous integration workflows** – build and test code.  
  3. **Publish workflows** – publish artifacts to repositories.  
- Templates cover many language/tool combos (e.g., Java + Gradle, Java + Maven) and can be customized.  
- Example use cases: auto‑greeting new contributors, auto‑labeling issues, etc.  
- Selecting a template (e.g., “Java Gradle”) creates a YAML file at `.github/workflows/` with pre‑configured logic that can be edited.  
- The workflow file includes a **name** for the workflow and **event triggers** that start the workflow when specified actions occur.

- Define events that trigger the workflow (e.g., push to `master`, pull request targeting `master`).  
- Other possible triggers: creating an issue, contribution joining, etc.; full list documented on the GitHub Actions events page.  
- Jobs are named groups of actions; names can be arbitrary.  
- First step: **checkout** the repository using the pre‑made GitHub Action `actions/checkout`.  
  - Actions are hosted as repositories on `github.com/actions`; each has its own YAML and versioning.  
- Second step: **setup‑java** action (another repository) to install the specified Java version (e.g., `1.8`).  
- Third step: run a command (`run` attribute) to change permissions of the Gradle wrapper file.  
- Fourth step: run `gradle build` in the same environment.  
- Workflow file (e.g., `ci.yml`) can be named freely.  
- Creating a new branch and opening a PR against `master` triggers the workflow as defined.  
- Execution details shown in the GitHub Actions UI:  
  - “Set up job” downloads the action repositories.  
  - Checkout action logs displayed.  
  - Setup JDK step logs shown.  
  - Build step logs show successful Gradle build.  
  - Post‑build actions (cleanup) run automatically even if not defined.  
- Overall, initial workflow setup is straightforward and hard to misconfigure.  
- Question raised: where are these steps actually executed? (addressed later).

- Workflows in GitHub Actions run on GitHub‑managed servers; no need to set up your own build environment.  
- Each job in a workflow gets a fresh GitHub server; one job runs on one server at a time.  
- Jobs run in parallel by default, but you can enforce sequential execution with the **`needs`** keyword (e.g., make a publish job depend on a successful build job).  
- The **`runs-on`** field selects the server OS: Ubuntu, Windows, or macOS.  
- Use a **matrix strategy** (e.g., `matrix.os: [ubuntu‑latest, windows‑latest, macos‑latest]`) to run the same job on multiple operating systems or tool versions.  
- After merging a PR, the workflow file in `.github/workflows/` is part of the repo; committing to `master` triggers the workflow, showing three parallel jobs on the three OSes.  
- Next step: take the built Java JAR, create a Docker image, and push it to a private Docker Hub repository.  
- Docker Hub provides one free private repository; the demo has two existing images and will receive the new Java demo image.  
- To build and push the image you can either write raw shell commands (Docker login, `docker build`, `docker push`) using YAML’s multiline pipe syntax, or use a pre‑made GitHub Action.  
- Ubuntu runners already have Docker installed, so no extra setup is required for Docker commands.  
- Search the GitHub Marketplace for a Docker build‑and‑push action; copy the usage example and supply parameters such as Docker Hub credentials, registry URL, and image name.  
- The chosen action includes a version tag (e.g., `uses: docker/build-push-action@v2`).

- The workflow can override parameters such as Docker registry name, image repository name, and image name.  
- Docker Hub registry is `docker.io`; the Docker ID and repository name are copied from Docker Hub.  
- Credentials (username and password) are required for GitHub to authenticate with the private Docker registry.  
- Secrets are stored in GitHub repository settings → **Secrets** and referenced in the workflow as `secrets.<SECRET_NAME>`.  
- Example: add Docker Hub username and password as secrets, then reference them in the YAML file.  
- Only the Ubuntu runner is needed (it has Docker pre‑installed).  
- The `docker/build-push-action` step handles building and pushing the Docker image automatically, without writing explicit Docker commands.  
- Optional overrides: tag name and Dockerfile location (default is current directory).  
- After committing the workflow file to the `master` branch, the GitHub Actions run shows steps “Built with Gradle” and “Built and push Docker images”.  
- The Docker Hub repository receives a new image tag (default tag includes the branch name as a prefix).  
- Tag can be overridden using the `tag` parameter.  
- The CI workflow builds the Java artifact, creates a Docker image, and pushes it to Docker Hub.
